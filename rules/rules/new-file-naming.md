## Naming a new file — take the name from whatever already does the job
- Before inventing a name for a new file, class, helper, service or migration, find the modules / packages that already do the same job and take **their** name, folder and internal structure. The closest semantic match wins, not the best name you can think of: a name you coined is a second convention, and the second convention is the defect.
- Read **several** siblings, not one. They usually carry a *family* of names rather than a single one; work out which family the new thing belongs to and follow the member whose job is closest. Then say which file you took the name and shape from, so the choice can be checked.
- The same applies to structure, not just the name: where the file sits, what it exports, and how it is wired up (barrel file, registration, startup call, DI) must match the precedent instead of a shape of your own.
- Only when nothing comparable exists anywhere is this a genuine first creation — and then **ask** before naming it: say that there is no precedent, propose the name and placement, and wait. Silently coining the first name of a new family is not yours to do, because every later module has to copy or contradict it.
- If the convention cannot be worked out from reading the siblings, say so and ask rather than guessing. "I could not derive it" is a cheap sentence; a wrong name spreads.
