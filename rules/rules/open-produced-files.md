## Produced files — open them, don't just print a path
- When a run produces a file whose whole point is to be **looked at** — a design or HTML page, a PDF, a report, a generated image or diagram, a chart, a screenshot that was asked for — open it on the user's screen instead of only naming its path.
- **PDF → a real PDF application** (the machine's PDF reader or editor), not a browser tab. **Everything else visual — HTML, PNG/JPG/SVG/WebP/GIF, plain text, Markdown → the browser.** Office documents (`.docx`, `.xlsx`, `.pptx`) → the system's default handler.
- **Resolve the application from the machine, never from memory.** The registered default is not necessarily the right one — a browser is commonly registered for `application/pdf`. Look at what is installed and what is registered (`xdg-mime query default <mime>` on Linux), prefer a dedicated PDF application when one exists, and fall back to the default handler when none does.
- **Detach it, always.** A GUI application started in the foreground blocks the session and dies with the terminal: Linux `setsid -f <app> <absolute path>`, macOS `open <path>`, Windows `start "" "<path>"`.
- **Still print the full absolute path in one piece** — opening replaces nothing, and the path is what lets the file be reopened by hand.
- **Open the deliverable only** — one window per file, never an intermediate or temporary artifact, never the same file twice, and nothing the user did not ask to see. When a run produces many files, open the one or two that are the result and list the rest.
- **No desktop session, no opening.** No `DISPLAY` / `WAYLAND_DISPLAY`, an SSH session, a container or a CI run → skip it and print the path. If the user says they do not want files opened, that holds for the rest of the session.
